# Changelog

All notable changes to this project will be documented in this file.

## Unreleased

### Added
- Benchmarks: the example benchmarks that open a database (`single_file_raw_bench`, `multi_writer_throughput_bench`, `multi_writer_vector_throughput_bench`, `query_core_bench`, `wal_perf_bench`, the replication benches and others) take `--mvcc` / `--no-mvcc` (default: the library default) and print the mode in their header. Every example benchmark, the Python raw benchmark and the TS benchmarks now exit with an error on an unknown flag or a missing or malformed value; unknown flags used to be ignored, so `single_file_raw_bench --mvcc` silently ran without MVCC. New `examples/bulk_load_bench.rs` measures bulk-load throughput (`--tx bulk|normal`, `--reader` to hold a read transaction open across the load).
- `KiteOptions::strict_schema(true)` (Rust) enforces `required` props on create and checks values against their declared `prop_type` on every create/update (int<->float coerced only when lossless), failing with the new `KiteError::SchemaViolation`. Off by default.
- CI runs Rust tests, clippy, rustfmt, and the Node (ava), Python (pytest) and Bun (playground, tui) suites on every pull request and push to main.
- `full_fsync` open option (Rust `SingleFileOpenOptions::full_fsync(true)`, Node `fullFsync: true`, Python `OpenOptions(full_fsync=True)`), off by default like SQLite's `PRAGMA fullfsync`. On macOS, `fsync` leaves writes in the drive's volatile cache, so `SyncMode::Full` alone survives application and OS crashes but not power loss. With `full_fsync`, Full-mode syncs use `F_FULLFSYNC`, which flushes that cache. It costs a few milliseconds per commit (about 300 single-writer commits/s instead of about 25k/s on an Apple SSD). Other platforms and sync modes are unaffected.
- Node: Promise-returning `*Async` variants of calls that block the event loop: `Database.checkpointAsync()`, `optimizeAsync()`, `vacuumAsync()`, `exportToJsonAsync()`, `exportToJsonlAsync()`, `importFromJsonAsync()`, `waitForTokenAsync()`, `VectorIndex.buildIndexAsync()`, `JsIvfIndex`/`JsIvfPqIndex.trainAsync()`, and the functions `createBackupAsync`, `restoreBackupAsync`, `createOfflineBackupAsync` and `pushReplicationMetricsOtel*Async`. They run on the libuv thread pool, reject (rather than throw) on bad arguments, reject inside a transaction (commit or roll back first), and `close()` fails while one is still running. The synchronous calls are unchanged; `waitForToken` and the OTEL pushes block the event loop for their whole wait or retry time.
- Node: vector inputs accept a `Float32Array`, read in place, as well as `number[]`: `VectorIndex.set`/`search`, IVF/IVF-PQ `insert`/`delete`/`search`/`searchMulti`/`addTrainingVectors`, `bruteForceSearch`, `Database.setNodeVector`, and Kite vector props. Setting 5000 768-dim vectors takes ~10x less time with `Float32Array`.
- Node: `strictSchema` in the Kite options turns on the strict schema mode; every prop declared without `optional()` is then required on create.
- Node: `KitePath.weight(prop)` and `shortestPath().weight(prop)` weigh edges by a numeric edge prop in `dijkstra()` and `kShortest()` (an edge without the prop weighs 1). Previously Kite's `dijkstra()` always counted hops.
- Node: `Database.transaction(fn)`, with the same async-context ownership as `Kite.transaction()`: while an async transaction is open, writes from other async contexts throw and other async transactions wait.
- Rust: `KitePathBuilder::weight_by_prop(name)` and `weight_fn(f)` weight `find()` and `find_k_shortest()` by a numeric edge prop or a closure. Previously the builder had no way to set weights, so every path was weighed by its hop count.
- Rust: traversal filters can see props through the new `TraversalProps` trait (`TraversalBuilder::execute_with_props` / `count_with_props`), and `api::schema` definitions convert into Kite's (`KiteOptions::try_from(&DatabaseSchema)`, `NodeDef::try_from(&NodeSchema)`, `EdgeDef::from(&EdgeSchema)`).
- `replication::progress::remove_replica_progress(sidecar_path, replica_id)` (Rust) forgets a decommissioned replica's progress. Previously a replica that stopped reporting pinned the primary's log retention forever, so its sidecar segments were never pruned.
- Export writes each node's labels (`labels`, sorted names) and import restores them. Exports written before labels were exported still import.
- Binary replication transports, with the snapshot's database copy and the log frames' payloads as raw bytes instead of base64 inside JSON: Rust `SingleFileDB::primary_export_snapshot_transport(include_data)` (a `SnapshotTransport`) and `primary_export_log_transport(cursor, max_frames, max_bytes, include_payload)` (a `LogTransportPage`); Node `exportReplicationSnapshotTransport` / `exportReplicationLogTransport` on `Database` and `Kite`, and `collectReplicationSnapshotTransport` / `collectReplicationLogTransport`, returning Buffers; Python `Database.export_replication_snapshot_transport` / `export_replication_log_transport` and `collect_replication_*_transport`, returning `bytes`. The JSON exports are now serializers over them. Exporting a 27 MB database in Node took 7 ms and 28 MB of extra memory instead of 77 ms and 183 MB through JSON, and the binary snapshot goes up to 1 GiB (JSON stays capped at 32 MiB).
- `primary_remove_replica_progress(replica_id)` on the database (Rust `SingleFileDB`, Node `Database` and `Kite` `primaryRemoveReplicaProgress`, Python `Database`) forgets a decommissioned replica's progress so it stops holding back log retention; it returns whether the replica had progress recorded.
- Both replication transports carry `generation`, the primary sidecar's log history as 16 hex digits, so a replica pulling over HTTP can detect a recreated sidecar and reseed, as file-based replicas do.
- Node: `Kite` has the replication methods `Database` had: `exportReplicationSnapshotTransport[Json]`, `exportReplicationLogTransport[Json]`, `primaryReportReplicaProgress`, `primaryRemoveReplicaProgress`, `primaryRunRetention`, `replicationMetricsPrometheus` and `replicationMetricsOtelJson`. The TS transport adapter (`createReplicationTransportAdapter`, `readReplication*Transport`) accepts a `Kite` as well as a `Database`, and gains `snapshotBinary()` / `logBinary()`.
- CI fails on RustSec vulnerabilities in `ray-rs/Cargo.lock` (`cargo audit`), and builds the docs site and server-renders every page on docs changes.
- Node: `VectorIndexOptions.annAlgorithm` (`'ivf'`, `'ivf_pq'` or `'auto'`, also exported as the `AnnAlgorithm` enum) chooses the `VectorIndex` backend, which Node users could not set before, and `VectorIndexStats.indexAlgorithm` reports the built one. Python: `VectorIndexOptions(ann_algorithm=...)` (the Python `VectorIndex` previously built only plain IVF), `SimilarOptions(rerank_factor=...)`, and `resolve_ann_algorithm(algorithm, dimensions, live_vectors)` for the auto rule.
- IVF and IVF-PQ training take an optional seed (Rust `IvfConfig::with_seed`, `IvfPqConfig::with_seed`, `VectorIndexOptions::with_seed`; Node `IvfConfig.seed`, also `VectorIndex`'s `ivf.seed`; Python `IvfConfig(seed=...)`, also the Python `VectorIndex`'s `ivf["seed"]`). With a seed, building over the same vectors gives the same index on any machine and thread count, down to identical `serialize()` bytes. Unseeded training (the default) still draws a fresh seed per build.
- Savepoints, for nested atomicity inside a write transaction: Rust `SingleFileDB::savepoint()`, `rollback_to(&savepoint)` and `release_savepoint(savepoint)`; Node `Database.savepoint()`, `rollbackTo(savepoint)` and `releaseSavepoint(savepoint)`; Python `Database.savepoint()`, `rollback_to(savepoint)` and `release_savepoint(savepoint)`. Rolling back to a savepoint undoes what the transaction did since: its writes, the schema names it defined (and its claims on them), and its MVCC writes, which then cause no conflict; the savepoint stays usable. While a savepoint is live the transaction's WAL records stay in memory, written once none is live or by the commit, so a rolled-back write never reaches the WAL. Taking a savepoint copies the transaction's pending changes. Using a savepoint outside its transaction, after releasing it, or after rolling back past it fails with the new `KiteError::InvalidSavepoint` (Python `TransactionError`).
- Rust: listings that seek instead of scanning. `SingleFileDB::nodes_after(after, limit)` and `edges_after(after, limit)` return a page of `list_nodes()` / the sorted `list_edges(None)` after a cursor; `out_edges_after` / `in_edges_after` return a slice of a node's edges (of one type, or all) after an `(etype, node)` key; `nodes_with_label`, `count_nodes_with_label` and `nodes_with_key_prefix` return the nodes with a label or a key prefix. Each returns what the full listing would, inside transactions and under MVCC too, and costs what it returns plus the changes since the last checkpoint. `streaming::NodeCursor` / `EdgeCursor` walk every node or edge in such pages.
- Rust: traversals read edges through the `NeighborSource` trait (`TraversalBuilder::execute_source`, `count_source`). A `Fn(node, direction, etype) -> Vec<Edge>` is one, `traversal::DbNeighbors` reads a database's edges lazily, and `traversal::edges_in_direction` lists a node's edges in a direction from its out- and in-edges.

### Changed
- **MVCC is now the default.** Rust `SingleFileOpenOptions` and `KiteOptions` (and so the recommended profiles), Node `Database.open`/`openDatabase` and `kite()`/`kiteSync()`, and Python `OpenOptions`, `Database` and `kite()` open with MVCC unless told otherwise. For code that relied on the old default:
  - Write transactions on several threads run at the same time instead of one after another. A commit that overlaps a write committed after its transaction began fails with a conflict (Rust `KiteError::Conflict`, Python `ConflictError`, Node an error reading `Transaction <id> conflict on keys: [...]`) instead of waiting; retry the transaction. Transactions that write different nodes and edges commit in parallel: 8 threads of 200-node transactions commit about 5.3K transactions/s, against 3.6K for one writer without MVCC.
  - Transactions are snapshot-isolated: a transaction reads the state as of its `begin` plus its own writes, never a commit made after it began. Reads outside a transaction still see the latest commit.
  - Each writable database runs a background GC thread for the version history (every `mvcc_gc_interval_ms`, 5 s by default); read-only opens start none, and closing does not wait for it. History is kept only while a transaction that can read it is open.
  - Costs against MVCC off: single-thread reads within about 2-7%, reads in read-only transactions about 6%, a single small writer about 7-8%, and about 30 µs more per writable open and close (the GC thread's start and stop).

  The file format does not change: existing databases open under the new default, and any file opens in either mode.
- **Non-MVCC mode is deprecated** and will be removed in a later release: `mvcc(false)` (Rust), `mvcc: false` (Node), `OpenOptions(mvcc=False)` (Python). It still works, with no runtime warning. The Rust setter is not marked `#[deprecated]`: it also takes `true`, and a warning on every call would break `-D warnings` builds.
- Bulk loads work with MVCC. `begin_bulk` (Node `beginBulk` and `bulkWrite`; Python `begin_bulk`, `Kite.bulk()` and `Database.batch_create_nodes`) failed with "bulk load requires MVCC disabled", and the Python and TS helpers silently fell back to a normal transaction; `bulkWrite` and `Kite.bulk()` now report a failing `beginBulk` instead of retrying. A bulk load runs alone among writers, in both modes: it waits for the open write transactions to finish, and write transactions that begin while it is open, or while it waits, wait for it. It records nothing for conflict checks and still writes its WAL records in one batch at commit. Readers never wait for it: reads outside a transaction see it whole once it commits, and a read transaction that began before its commit does not see it. Loading 200k nodes and 1M edges (2 props each) in transactions of 5000 runs at about 1.5M nodes/s and 0.6M edges/s with MVCC on or off (a normal MVCC transaction loads nodes about 20% slower). With a read transaction open across the load, each commit keeps version history for it, and the load runs at about 1.25M nodes/s and 0.38M edges/s.
- **Snapshot format v5**: the node-id map switches to a sparse sorted table when ids are spread out, and section sizes and string offsets are 64-bit. Huge custom node ids (e.g. 3e9, 2^40, `i64::MAX`) no longer make checkpoints and opens allocate gigabytes or leave the database unopenable, and sections beyond 4 GiB round-trip. v4 databases still open and are upgraded at the next checkpoint; older releases cannot open v5 snapshots.
- Node keys are unique: creating a node (single, by id, or in a batch) with a key held by a live node fails with `DuplicateKey`. Upserts still resolve to the existing node.
- Adding an edge whose source or destination node does not exist fails with `NodeNotFound`; re-adding an existing edge is a no-op. Setting properties on a missing node or edge fails with `NodeNotFound` / the new `EdgeNotFound`.
- Explicit node ids above `i64::MAX` are rejected, and the id allocator returns an error instead of wrapping. The Node and Python bindings reject negative, fractional, NaN/Infinity and (Node) above-`Number.MAX_SAFE_INTEGER` ids.
- `VectorIndex` normalizes stored vectors only for cosine by default; Euclidean and dot-product indexes keep raw vectors. In Rust, `IvfIndex`/`IvfPqIndex` `search`, `search_multi` and `delete` now return `Result`.
- TS: an async `transaction()` no longer absorbs writes from other async contexts. Outside writes and sync transactions throw; outside async transactions wait their turn. Node props named `id`, `key` or `type` are rejected at schema definition.
- `create_node`, batch `CreateNode` and `TxContext::create_node` keep properties outside the node schema, consistent with insert/upsert/set_prop, and declared defaults are applied on every create path.
- Backup blocks commits and checkpoints while it copies, fsyncs the result, and requires no open transaction on the calling thread. Restore writes a temp file and renames it into place, and refuses a target that is open.
- **On-disk format**: the database file now stores two checksummed header pages (pages 0-1) with the WAL starting at page 2, so a torn header write can no longer make a database unopenable. Existing single-header files are migrated automatically and crash-safely (temp file + atomic rename) on their first writable open; read-only opens of legacy files work without migration. Releases up to v0.2.18 read only the first header page, so do not open a converted file with them.
- Checkpoints are copy-on-write: the new snapshot is written to a fresh region and fsynced before the header flips, so a crash mid-checkpoint can no longer destroy the only valid snapshot. Retired snapshot regions are reused when the next snapshot fits, keeping file growth bounded; vacuum still performs full compaction.
- Writable opens take an exclusive file lock (shared for read-only), preventing two processes from corrupting the same database. Replica bootstrap reads a live primary without taking its lock.
- `read_only` opens are now truly read-only: no write permission is requested, recovery that would need to write returns a clear error, and close does not touch the file.
- IVF-PQ approximate search now computes distances in each metric's native space (L2, cosine with reconstructed-norm correction, dot product), matching the exact search path's ranking and scores. The unused precomputed centroid-distance table is no longer written (a format flag keeps older payloads readable).
- The WAL size is optional when reopening a database. `SingleFileOpenOptions.wal_size` is now `Option<usize>` (default `None`): an existing file opens with the WAL size recorded in its header, and a new file gets the 4MB default. An explicit size (`.wal_size(n)`, unchanged) still creates new files with that size and rejects existing files whose WAL differs. The Node (`walSize`, `walSizeMb`) and Python (`wal_size`) options follow the same rule when left unset. Rust code that reads or assigns the field directly must now handle an `Option`.
- Writers that fill the WAL's secondary region while a background checkpoint runs now wait for it to install instead of failing with `WalBufferFull`. The auto-checkpoint can also run after a failed commit, after a rollback, and in `begin` when the WAL is full.
- `background_checkpoint()` returns the new `KiteError::CheckpointDeclined` when it declines to start (previously `WalBufferFull` or `InvalidWal`).
- **On-disk format v2 (WAL salts)**: each WAL region has a salt in the header, mixed into every record's checksum and replaced whenever a checkpoint, compaction or background checkpoint reuses the region. After a crash, records of an earlier WAL cycle left on disk could pass their checksum and be replayed over newer acknowledged commits; now they end the scan. Version 1 databases open and replay as before and switch to v2 at their next WAL reset (a checkpoint, compaction, or the start of a background checkpoint); new databases are created as v2. As with the dual-header change, do not open converted files with releases up to v0.2.18: they don't check the format version, and would fail every salted WAL record's checksum and lose the commits since the last checkpoint.
- Opening a database checks the header's format version, minimum reader version and flags. A file that needs a newer reader, or uses a flag this version doesn't implement (such as encryption), fails with a clear error (`VersionMismatch` for versions) instead of being misread or written. A newer format that declares this version a capable reader opens read-only only.
- Group commit (`group_commit_enabled`, Normal sync mode) batches commits: those that arrive while a batch is being written are written together with one WAL flush and one header write, and no commit sleeps while holding the commit lock. `group_commit_window_ms` is still accepted but no longer used.
- Replicas reject local data writes (nodes, edges, properties, labels, vectors) with `InvalidReplication`. Previously a replica accepted them and silently diverged from its primary. Schema definitions still work, so a Kite opened on a replica can define the names it uses.
- Node: `JsPropValue.intValue` is `number | bigint`. Integers beyond `Number.MAX_SAFE_INTEGER` read back as a BigInt instead of a rounded number (Database `getNodeProp`/`getEdgeProp`/`getNodeProps`, Kite `getProp` and Kite node objects); safe integers stay numbers. TypeScript code doing arithmetic on `intValue` must narrow it.
- Node: invalid numbers are rejected instead of silently coerced: BigInt prop values outside the i64 range (previously wrapped); u32 arguments (edge types, prop keys, label ids, `k`, depths, limits, `walSize`, `pageSize`, `minSize`) that are negative, fractional, NaN or above 2^32-1 (previously `-1` became 4294967295 and NaN became 0, so `addEdge(a, -1, b)` stored an edge of a nonexistent type and `walSize: -1` created a 4 GB WAL); a `JsPropValue` missing the field its `propType` names (previously stored 0, false or ""); and a `number[]` prop, stored as an f32 vector, holding an integer f32 cannot represent exactly. BigInt key fields keep all their digits. `addEdgesBatch` takes `JsFullEdgeInput` (a `JsFullEdge` still fits).
- Node: `getNodesPage`/`getEdgesPage` reject a malformed cursor instead of restarting from the first page, and edge pages follow (src, etype, dst) order.
- TS: `node()` throws when a key function does not return `<prefix>${id}`. Key functions are only probed for their prefix, so one like ``(id) => `user:${id}:v2` `` silently stored `user:<id>`, and a validating one failed with its own error. Use a template or parts key spec for other key shapes.
- TS: `bulkWrite`'s `chunkSize` and `batchAdaptive`'s `maxBatch`/`minBatch` must be positive integers. Previously `chunkSize: NaN` looped forever, `maxBatch: NaN` silently dropped every operation, and `0` was treated as 1.
- Node: `KitePath.direction()` accepts any letter case, including `TraversalDirection.In`, and throws on unknown values. Previously anything but lowercase `'out'`/`'in'`/`'both'` silently meant `'out'`.
- Python: errors from the native module are `kitedb.KiteError` (a `RuntimeError` subclass, so `except RuntimeError` still works) or a subclass that names the cause: `ConflictError`, `ReadOnlyError`, `NotFoundError`, `ClosedError`, `TransactionError`, `DuplicateKeyError`, `LockError`, `CorruptionError`, `WalFullError`. Previously every error was a bare `RuntimeError`.
- Python: `stream_nodes`, `stream_nodes_with_props`, `stream_edges` and `stream_edges_with_props` return lazy iterators that build one batch at a time, instead of building every batch for the whole database (under the GIL) before returning a list. Memory now stays proportional to one batch (about 150 MB down to 3 MB for 200k nodes with props) and the first batch arrives in milliseconds. Use `list(...)` if you need the old list of lists.
- Python: an unknown traversal `direction`, vector `metric` or multi-query `aggregation` raises `ValueError`. Previously it silently fell back to `out`/`both`, cosine or min.
- Python: `kite()` defines a label per node type and attaches it to nodes it inserts or upserts, like the Rust and Node Kite. `Database.batch_create_nodes` takes optional `labels`.
- Python: the package declares `requires-python >=3.9` (wheels are built for 3.9-3.13); it claimed 3.8 support.
- Rust: `strict_schema` also type-checks declared edge props on `link_with_props`, `set_edge_prop(s)`, `update_edge`, `upsert_edge` and batch edge ops.
- Rust: with overlapping key prefixes (e.g. `user:` and `user:admin:`), a key belongs to the type with the longest prefix. Creating a `User` keyed `admin:x` fails with `InvalidSchema`, and `get("User", "admin:root")` returns `None` instead of the `Admin` node. Types that share a prefix are told apart by their type label.
- Rust: `Kite::has_path` takes `&self`. The unused `kitedb::api::builders` module is removed.
- Rust: the `kitedb::util::crc` functions are named for the checksum they compute, CRC-32 (IEEE), not CRC-32C: `crc32c`, `crc32c_chunked`, `crc32c_multi`, `verify_crc32c` and `Crc32cHasher` are now `crc32`, `crc32_chunked`, `crc32_multi`, `verify_crc32` and `Crc32Hasher` (also `kitedb::util::crc32`). The old names are removed. Checksums and the file format are unchanged, and the replication transport JSON keeps its `checksum_crc32c` field.
- Opening a snapshot checks more, and refuses with `InvalidSnapshot`: compressed sections whose declared sizes contradict the header counts, or that together would inflate to more than 1024 times the snapshot's size (and more than 64 MiB); string ids one past the string table; a node id table and its inverse that disagree; and a key index without buckets whose entries are not sorted by hash. Snapshots KiteDB writes pass these checks: with compression on, a section is now stored uncompressed when compressing it would exceed the inflation limit. No format change.
- A checkpoint given the same node id twice now fails with `InvalidSnapshot` instead of writing a snapshot in which one of the two nodes is unreachable.
- Opening a snapshot also refuses, with `InvalidSnapshot`, one whose physical nodes are not in node ID order. Pages and edge slices find their start by binary search on that order, so such a file would have paged out of order. Snapshots KiteDB writes are always in order, and the check costs nothing measurable (it rides on the existing walk of the node ID map).
- Opening a database with a large snapshot is 4-5x faster again. Since opens began checking the whole snapshot (above), they inflated every compressed section (checkpoint compression is on by default) and then checked each one, all on the calling thread, so a read-only open of a checkpointed 100,000-node, 200,000-edge graph took about 11 ms instead of about 2 ms. Opens now inflate and check sections on up to 8 threads, checking each section right after inflating it, compute a large snapshot's checksum in parallel chunks, and check arrays with a vectorized pass first (the entry-by-entry pass runs only to name what failed). That graph now opens in 2.2 ms on an M5 Pro and 2.7 ms on 4 Linux cores (was 10.3 ms), and a 1M-node, 5M-edge one in 46 ms instead of 193 ms; uncompressed snapshots open about 4x faster too. A snapshot with less than about 512 KiB to inflate stays on the calling thread. Opens check exactly what they checked before, and refuse a corrupt snapshot with the same error.
- OTLP metrics push (HTTP and gRPC) and protobuf rendering moved behind a new `otlp` Cargo feature, so Rust users building with `default-features = false` no longer compile tokio, tonic, ureq, rustls and opentelemetry-proto. The `napi` and `python` features enable it, so the bindings are unchanged; Rust code that calls the `push_replication_metrics_otel_*` or `*_otel_protobuf*` functions without the bindings must enable `otlp`.
- Export pauses commits and checkpoint installs while it reads, as backup does, so an export is one point in time. Previously an export taken under writes could hold an edge whose endpoint it did not hold.
- Replication primary manifests carry a random generation id. A replica whose primary's sidecar was deleted and recreated now reports `needs_reseed` (previously a replica at log 5 silently skipped the new sidecar's frames 1..5), and its reseed follows the new sidecar.
- Full-sync primaries no longer sync the sidecar directory on every commit (only the manifest's contents; a head reverted by a crash is recovered from the segment on open), about halving commit time with replication on macOS.
- Reads no longer take a process-wide lock to find the calling thread's transaction (each thread keeps its open transactions in thread-local storage), so they no longer wait for other threads' begin, commit or rollback.
- Without MVCC (now deprecated: MVCC is the default, see above), write transactions now run one at a time: a write `begin` (or a `transaction()`/`batch()` that begins one) waits until no other thread has a write transaction open. Concurrent write transactions had no conflict detection, so two read-modify-write transactions on one property silently lost an update, and an edge or vector added to a node another transaction was deleting could commit pointing at a node that no longer existed. Read-only transactions never wait, and MVCC mode keeps concurrent writers with commit-time conflict detection, so several writer threads need MVCC. On the bundled 8-thread benchmark (200-node transactions), non-MVCC throughput fell from about 1.8K to about the single-writer rate, 1.2-1.4K transactions/s. In Python a waiting `begin` releases the GIL.
- `count_nodes()` no longer lists and sorts every node id: it starts from the snapshot's node count and adjusts for the nodes the uncheckpointed changes, the caller's open transaction, or MVCC version history name. On 100,000 checkpointed nodes it takes about 10 µs instead of about 5 ms, with the same result as `list_nodes().len()`.
- A background checkpoint now replays the commits made since it started before it takes the commit lock to install, and replays only the few that land meanwhile under it, so commits wait less at its install (with one thread committing nonstop during a checkpoint of a 100,000-node graph, the longest commit wait fell from 24-32 ms to 13-19 ms; what remains is moving those commits' WAL records).
- Commits do less WAL I/O. A commit no longer reads the WAL page holding the head back from disk and rewrites whole pages: it writes exactly the bytes it appends, with one write per contiguous range (a one-node commit makes one WAL write and no read; before, a read and a write per page touched). Each WAL record is encoded and checksummed once (it was twice), and a transaction keeps a copy of its records only for a bulk load or the replication sidecar. On the new `examples/wal_perf_bench.rs`, Normal-mode one-node commits went from about 195k to about 222k per second on an Apple SSD.
- `SyncMode::Full` commits (and checkpoint header installs) sync with `fdatasync` where the OS has it (Linux, the BSDs), which makes the written bytes durable without also flushing timestamps, as SQLite does. The first sync after anything changed the file's length (WAL or snapshot allocation, truncation) is still a full `fsync`. macOS keeps `fsync`, or `F_FULLFSYNC` with `full_fsync`.
- Opening a database reads only the live part of the WAL, with one read per pass, instead of every WAL page one at a time wherever the head was, and a writable open checks each WAL region in one pass (it read the live WAL twice to check it before replaying it). With 16 small commits, a 64 MiB WAL opened in 0.1 ms instead of 12 ms, and a 256 MiB one in 0.1 ms instead of 47 ms; with a nearly full WAL, a writable open took about 30 ms instead of about 60 ms (46 MiB live in a 64 MiB WAL) and about 100-140 ms instead of 224-278 ms (182 MiB live in a 256 MiB WAL). WAL scans during checkpoints likewise read a region with one read instead of one per page.
- A background checkpoint's install moves the commits made since it started back to the start of the WAL with one write of their records as they are (re-salted), reusing the records its replay read before taking the commit lock. Before, it decoded and rebuilt every record, read each WAL page before writing it, and wrote page by page, all under the lock. The replay also parses those records after releasing the WAL lock, which every commit takes, instead of holding it for the parse (about 2 ms for 1.4 MB of records in a debug build, now about 0.15 ms). With one thread committing nonstop during a checkpoint of a 100,000-node graph (release build), the install held the commit lock for 1.6-2.6 ms instead of 4.7-6.8 ms, and the longest commit wait fell from 5-7 ms to 3-4 ms.
- Vector search is faster: distance kernels use NEON on Apple Silicon/ARM and AVX+FMA on x86 (3.5-7x per distance at 128-1536 dims); k-means++ initialization runs in parallel and training samples at most 256 vectors per cluster, so building an IVF index over 100K x 128-dim vectors took 0.8 s instead of 8.3 s and IVF-PQ 5.6 s instead of 20.7 s; exact (brute-force) search keeps a bounded top-k instead of sorting every vector (about 4x faster at 100K vectors).
- `VectorIndex` retrains its ANN index on the next search once the live vector count reaches 4x the count it was trained on. Previously it trained once at the training threshold, so a growing index kept its initial cluster count and each probe scanned an ever larger share of the corpus (after growing from 1K to 64K vectors, searches took 0.27 ms instead of 1.76 ms).
- Rust: `VectorStoreConfig::with_metric` resets `normalize_on_insert` to the metric's default (on only for cosine), like `VectorIndexOptions::with_metric`; call `with_normalize` afterwards to override. `KMeansError` has a new `InvalidInput` variant (zero clusters or dimensions).
- An IVF `n_probe` of 0 (in the index config or per search) probes one cluster instead of silently returning no results. Vector stores reject a `row_group_size`, `fragment_target_size` or dimension count of 0 on insert.
- IVF-PQ indexes over a dimension with no divisor near the requested PQ subspace count (e.g. a prime like 97) use one subspace per dimension instead of a single subspace, which had collapsed recall (recall@10 0.98 instead of 0.22 at 97 dims).
- `VectorIndex` picks its ANN backend by size by default (new `AnnAlgorithm::Auto`, Node `annAlgorithm: 'auto'`, Python `ann_algorithm="auto"`): plain IVF while the collection has fewer than 50,000 live vectors or fewer than 512 dimensions, IVF-PQ from there on, decided at each build. Small and low-dimensional collections now get exact distances and much faster builds (previously every index was IVF-PQ: at 128 dims and 10K vectors, plain IVF searches in about half the time, builds about 20x faster, and keeps no PQ codes). Large high-dimensional ones keep IVF-PQ, which searched about 2x faster there (2.1-3.6x at 512-1536 dims and 50K-100K vectors). A growing index switches from IVF to IVF-PQ when it crosses the threshold, rebuilding on the next search; a shrinking one keeps its backend until its next rebuild. `AnnAlgorithm::Ivf` / `IvfPq` (Node `'ivf'` / `'ivf_pq'`, Python `"ivf"` / `"ivf_pq"`) still force either, and `stats()` reports the built backend (`index_algorithm` / `indexAlgorithm`). Rust code that matches on `AnnAlgorithm` exhaustively needs an `Auto` arm. The Python `VectorIndex` also rebuilds at 4x growth now, like the Rust one.
- IVF-PQ search re-ranks its best `max(k * 4, 80)` PQ candidates by exact distance to the stored vectors, so results carry exact distances and thresholds apply to them. Ranking by PQ distance alone had held recall@10 on clustered 128-d data to 0.68 at 10K vectors and 0.53 at 100K; it is now 1.0 and 0.97, for 10-15% more search time. The over-fetch factor is configurable per search (Rust `IvfPqSearchOptions::rerank_factor` / `SimilarOptions::with_rerank_factor`, Node `rerankFactor`, Python `SearchOptions(rerank_factor=...)`); 0 restores the PQ-only ranking. The PQ scan also looks up a vector's node only when it could rank, which made IVF-PQ searches about 20-30% faster at 10K-100K vectors.
- `ray-rs/Cargo.lock` is committed, so CI and release builds resolve the same dependency versions. memmap2 must be at least 0.9.11 (RUSTSEC-2026-0186), and rustls, rustls-webpki, h2 and crossbeam-epoch are on patched releases.
- Playground: `GET /api/replication/snapshot/latest?includeData=true` refuses databases larger than `PLAYGROUND_SNAPSHOT_MAX_BYTES` (default 32 MiB) instead of loading any size into memory, and `/api/replication/metrics` names its series `kitedb_replication_*` (was `raydb_replication_*`), like core's exporter.
- The replication snapshot transport no longer exposes `db_path` (the primary's absolute path), and its `start_cursor` is the position right after the snapshot's head frame. It was `epoch:0:0:retained_floor`, so a replica that pulled the log from it replayed frames the snapshot already held. The TS `ReplicationSnapshotTransport` type drops `db_path` and gains `generation`.
- The replication snapshot transport copies the database under the commit lock and checkpoint gate, as backups do, so the copy is consistent and holds exactly the commits up to its `head_log_index`; commits wait for the copy, and calling it with a transaction open on the same thread fails with `TransactionInProgress`. Previously it read the live file: under concurrent writes it could hold a commit whose frame was not appended yet (which a replica then applied twice), and on a `SyncMode::Off` primary it held none of the commits since the last checkpoint.
- Replica snapshot bootstrap commits in batches of about 10k writes (or 1/8 of the replica's WAL) instead of one transaction for the whole graph, keeping the replica marked incomplete until its cursor is set, and checks that the source stayed quiet from the file's length, modification time and header pages instead of checksumming the whole file three times per attempt. Bootstrapping 200k nodes took 0.9 s and 332 MB at peak instead of 4.4 s and 523 MB (with a WAL large enough for the old single transaction). A bootstrap that runs out of attempts on a torn read of a source that kept changing (a frame or WAL record half written) now fails with a "did not quiesce ... quiesce writes and retry" error naming the read error, instead of the bare read error.
- Replica catch-up applies each contiguous run of frames in one transaction (split at 1/8 of the replica's WAL) instead of one transaction per frame. In Full sync mode it applied 230k frames/s instead of 4-7k. A failing run is retried frame by frame, so the frames before the failing one still apply.
- The replication sidecar follows the database's sync policy: it syncs with a plain `fsync`, and with `F_FULLFSYNC` only under the `full_fsync` opt-in in Full mode. It used `File::sync_all`, which is `F_FULLFSYNC` on macOS, for every commit's frame and manifest (and for replica cursors and progress), so a Full-mode commit with replication took 8.9 ms instead of 0.27 ms on an Apple SSD. Full mode still syncs each commit's frame before the commit returns; Normal and Off still sync frames at checkpoint and close.
- Rust: `PrimaryReplication::open_with_recovery` takes a `replication::durability::SidecarSync` (the sync mode and `full_fsync`) instead of a `SyncMode`.
- The single-file cache layer is removed. No read ever consulted it, so enabling it (`SingleFileOpenOptions::cache` / `enable_cache()`, `cacheEnabled` in Node, `cache_enabled` in Python) gave zero hits and only added a global lock and invalidation work to every write. The cache options (`cacheEnabled`, `cacheMaxNodeProps`, `cacheMaxEdgeProps`, `cacheMaxTraversalEntries`, `cacheMaxQueryEntries`, `cacheQueryTtlMs`, and the Python `cache_*` equivalents) are still accepted but have no effect and are no longer range-checked. For one release the Node and Python `cache*` database methods remain as deprecated no-ops (`cacheIsEnabled()` returns false, `cacheStats()` returns null/None), and metrics report `cache.enabled = false` with zero counts and `memory.cacheEstimateBytes = 0`. The `cache_efficiency` health check is gone. `VectorIndex` no longer keeps its write-only node cache, so its `cache_max_size` / `cacheMaxSize` option has no effect either and Node no longer range-checks it. The Python `OpenOptions.cache_snapshot` and Rust `types::OpenOptions::cache_snapshot` never had an effect (an open database always keeps its snapshot mapped); they stay accepted and deprecated.
- **Breaking (Rust):** the `kitedb::cache` module (`CacheManager`, `LruCache` and the property, traversal and query caches), `types::CacheStats`, the `SingleFileDB::cache_*` methods, and `metrics::CacheMetrics`, `metrics::CacheLayerMetrics`, `DatabaseMetrics::cache` and `MemoryMetrics::cache_estimate_bytes` are removed. `SingleFileOpenOptions::cache`, `cache()`, `enable_cache()` and the `CacheOptions` / `*CacheConfig` types remain, deprecated and without effect.
- MVCC costs about nothing on reads: reads outside a transaction no longer take the transaction manager or version-chain locks, reads in a transaction take the version chains (now a shared lock) only when a commit since their snapshot recorded history, and read-only transactions no longer record what they read. Single-thread `node_prop`, `node_props` and `out_edges` with MVCC on run within a few percent of MVCC off (previously up to 28% slower, and up to 50% with 4-8 reader threads), reads in a read-only transaction within about 6% (previously about 70% slower), and an old snapshot's `node_props` looks up only that node's history instead of scanning every chain.
- MVCC writes cost about what conflict tracking needs: a commit with no other transaction open no longer indexes its writes or checks conflicts, and no commit records version history for the props, labels, key and edges of nodes it creates. Single-writer small transactions with MVCC on went from about 33% to about 8% slower than MVCC off; a single MVCC writer of 200-node transactions from about 700 to about 1,500 transactions/s (one non-MVCC writer: about 1,700), and 8 concurrent MVCC writers from about 550 to about 1,200.
- Concurrent MVCC writers scale. A commit no longer re-inserts each change into the committed delta under its lock (a transaction's new nodes, their edge patches and new edges' props move in whole, and the delta's maps hash with foldhash instead of SipHash), no longer indexes every key it wrote for conflict checks (recent commits keep their write sets whole, found through per-node key groups that the committing thread computes before taking a lock), and writers no longer take the transaction manager's lock to note what they write. On `multi_writer_throughput_bench` with 200-node transactions, 4 MVCC writers went from about 1,300 to about 4,800 transactions/s and 8 from about 1,250 to about 5,500, where one MVCC writer went from about 1,550 to about 3,100 and one non-MVCC writer from about 1,750 to about 3,650. One-node transactions gain about 10% with one writer, but 4 or 8 writers still commit about half as many as one.
- MVCC keeps version history only while a transaction that can read it is open: `mvcc_retention_ms` now defaults to 0 (was 60 000). Nothing reads older history, so the old default only held memory, up to a minute of every write made while another transaction was open.
- MVCC GC no longer holds the transaction manager while it prunes version chains, and opening an MVCC database no longer builds version chains for the WAL's commits (GC dropped them right away).
- Pages seek to their cursor instead of listing every node (or listing and sorting every edge) for each page: `streaming::nodes_page_single` / `edges_page_single`, Node `getNodesPage` / `getEdgesPage`, Python `get_nodes_page` / `get_edges_page`. On 1M nodes and 5M edges after a checkpoint, page 1000 of 100 nodes takes about 1 µs instead of 6.6 ms, and of 100 edges about 3 µs instead of 87 ms; with every change still in the WAL, 9 ms instead of 24 ms and 3.3 ms instead of 317 ms. Node pages read their `total` from the node or edge count, separately from the page, instead of counting the listing.
- `count_edges()` no longer lists every edge: it starts from the snapshot's edge count and adjusts for the changes since the last checkpoint (5M checkpointed edges: under a microsecond instead of 67 ms), with the same result as `list_edges(None).len()`. Inside an MVCC write transaction, and for an MVCC reader that reads version history, it still lists them.
- `Kite::all(type)` and `count_nodes_by_type` resolve the type only of the nodes whose key has the type's prefix or that carry its label, read in one pass over the snapshot's keys and labels plus the changes since the last checkpoint, instead of reading every node's key. On 100k nodes of 5 types they take 3.6 ms instead of 9.3 ms after a checkpoint (8.3 ms instead of 15 ms before one), with the same results.
- Traversals with a limit read the edges of their last step lazily (Rust `Kite`, and the Node `Database` and `Kite` traversals without `whereEdge`/`whereNode`): `take(1)` from a node with 200k out-edges takes under a microsecond instead of 7 ms. Typed neighbor reads (Kite `neighbors_out(node, Some(type))`, `out_neighbors`, `has_out_edges` and the in-edge forms) read only that type's edges instead of every edge of the node.
- Python: `stream_nodes*` and `stream_edges*` walk the database by cursor, reading a batch (or the changes since the last checkpoint) at a time, instead of listing every node id or edge when the stream starts. A node or edge created past the cursor during the stream is now listed, and one deleted before it is read is not.
- The Node `Database` traversals and pathfinding, `JsGraphAccessor` and the Python traversals list a node's edges with the same code as Kite, so `Both` lists a self-loop once. They listed it twice; traversals skip nodes they have visited, so their results did not change.

### Fixed
- Python: a commit that fails inside `Kite.transaction()`, `Kite.batch()` or `Kite.bulk()` (a `ConflictError`, for one) raises that error. They rolled back the transaction the failed commit had already ended, which raised `TransactionError('Failed to rollback: No active transaction')` in its place.
- Commits no longer wait for a background checkpoint to write and sync its new snapshot. It wrote and synced those pages holding the lock every commit takes to append to the WAL, so under I/O load, with a slow fsync, every commit stalled for the length of the snapshot's sync; they are now written through a second file descriptor. The checkpoint's cut and install still pause commits for their own fsyncs.
- A replication primary superseded by a promotion while its commit waited for the commit lock (behind another commit or a checkpoint) no longer commits locally: the epoch fence is checked under the commit lock. Previously the check ran before the lock, and such a commit landed locally while its sidecar append failed, so no replica ever received it.
- Reopening a replication primary in a process that spawns child processes no longer fails at random with "primary sidecar lock is held by another process". Closing the primary released the sidecar's `primary.lock` only by closing its descriptor, and a child spawned at that moment holds a copy of that descriptor until its exec completes (or for its whole life if it forks without exec), which kept the lock held. With 4 threads spawning processes, about 12 of 1000 close-and-reopen cycles failed. Closing now unlocks it explicitly, as it already did for the database file.
- A replica in `SyncMode::Normal` or `Off` no longer skips frames after a crash. Its cursor file was synced as soon as it was written, but not the commits it covered (Normal mode wrote their WAL and header without a sync; Off mode kept them in memory), so after an OS crash (any process crash in Off mode) the cursor said frames were applied whose data was gone, and catch-up went on past them; the same held for the cursor a snapshot bootstrap set. The replica now writes and syncs its applied commits before it writes the cursor, once per pull (in Normal mode a pull of 256 frames took 0.75-0.85 ms instead of 0.75; no format change).
- A replica bootstrapping or reseeding from a live primary no longer crashes with SIGBUS when the primary checkpoints meanwhile. The replica read the primary's database file through a memory mapping of its snapshot, without the primary's lock; a checkpoint that placed its new snapshot in earlier free pages truncated the old one from the end of the file, and the replica's next read of the mapping killed the process (about one run in five of a test bootstrapping under steady primary writes and checkpoints). A database opened without its file lock (the replica's view of its primary, or the multi-node simulation option) now copies its snapshot into private memory instead of mapping it, so a concurrent change is retried rather than fatal; the copy costs memory the size of the snapshot while the bootstrap runs. Databases opened normally still map their snapshot.
- Bootstrapping a replica from a source graph larger than the replica's WAL no longer fails with `WalBufferFull` (the whole copy was one transaction; 200k nodes failed with the default 4 MB WAL).
- Playground: `GET /api/replication/transport/snapshot` and `/api/replication/transport/log` work. They called methods the connected `Kite` did not have and always answered "Replication method unavailable". `snapshot/latest?includeData=true` returns a consistent copy through the snapshot transport instead of reading the live file.
- A crafted snapshot whose compressed sections declare gigabytes no longer makes open allocate them before failing (a 57 KiB file could make it try to inflate 1.75 GiB).
- Reads from zstd-compressed snapshots no longer take a lock and a hash-map lookup on every section access, and open inflates each section once into a buffer of its exact size instead of copying it twice. On a 200k-node graph, `has_edge` from 8 threads went from 1.4M to 159M ops/s, single-threaded reads got 3-17x faster, and open allocates 51 MiB instead of 193 MiB.
- Opening a snapshot no longer allocates a 24-byte cache slot per string (about 1.2 GB for 50M keyed nodes), and key lookups no longer allocate.
- Checkpoints use less memory and time: the snapshot writer's peak heap dropped from 3.5x to 1.9x the snapshot size (7.6x to 3.0x with zstd), and it builds about 3x faster.
- `check_snapshot` now checks the invariants reads rely on: in-edge order, key bucket membership, key hashes, key entries against node keys, schema id ranges and UTF-8 strings. It no longer reports duplicate edges or empty snapshots as corrupt, checks the string table when there is no key index, and its edge check is O(E log N) instead of O(E x in-degree) (a node with 20k in-edges: 934 ms -> 3 ms).
- `check()` (Rust `SingleFileDB::check` and `Kite::check`, Node and Python `check()`) now runs `check_snapshot` on the database's snapshot and reports its findings prefixed with `snapshot: `. Before, it compared only what the graph API lists, so a snapshot with a wrong key hash, unsorted adjacency or mismatched in- and out-edges checked valid. Label, edge type and property key IDs that were never defined are warnings, not errors: the low-level `add_edge`, `add_node_label` and `set_node_prop` accept them, so a database built that way still checks valid.
- Checkpoints, background checkpoints and optimize now compact vector stores. Deleting or replacing a vector only marked it deleted in its fragment, and nothing ever removed it, so deleted vectors stayed in memory and in every snapshot for good. A checkpoint now drops fully deleted fragments and copies the live vectors of fragments that are at least 30% deleted into new ones. In a test with 640 stored vectors, 480 of them deleted, the store went down to the 160 live ones. Vector ids stay the same.
- In `SyncMode::Normal`, a commit that returned an error because its header write failed could come back after an OS crash or power loss. Its records stayed in the WAL file, still valid, and the next commit overwrote them and wrote its header without a sync in between, so the crash could keep the header and lose the overwrite. The failed records are now zeroed and synced right away; if that sync fails, the next commit syncs before writing its header. `SyncMode::Full` was not affected.
- A `SyncMode::Off` database dropped without `close_single_file` no longer loses every commit since the last checkpoint: dropping the handle now flushes the WAL and writes the header as close does, best effort (it never panics; failures go to stderr). The `SyncMode::Off` docs now say plainly that commits stay in memory until a checkpoint, close or drop, so even a process crash loses them.
- Opening a database whose header (checksum intact) names WAL positions outside their regions now fails with `InvalidWal`: an active region other than 0 or 1, a tail past the head, a secondary head before its region, or a head past the WAL. Previously the open succeeded, and the WAL usage computation underflowed later, panicking in debug builds and leaving the WAL permanently "full" in release builds.
- WAL replay no longer silently skips a record whose checksum passes but whose payload does not parse. A crash cannot produce such a record; a buggy or incompatible writer can. Skipping it applied the rest of its committed transaction without it. Open now fails with `InvalidWal` instead. Torn tails are handled as before, but open now logs how many bytes it drops after the last valid record.
- Creating a database no longer truncates one that another thread or process created at the same path, between this open's existence check and its file lock; the open now opens that database. A new database's directory is fsynced, so the file can no longer vanish after a power loss. The legacy single-header migration syncs its directory the same way. Previously it failed for a bare relative file name, whose parent path is empty.
- Databases past 1 GiB: a checkpoint whose snapshot reached the page at offset 1 GiB failed (leaking its pages until the next vacuum), and a WAL of 1 GiB or more was allocated after that page while the header named page 2. The page was reserved for SQLite-style lock bytes, which KiteDB never uses (it locks the whole file); the reservation is gone. Releases up to v0.2.18 still refuse to write that page, so on a file whose WAL or snapshot covers it they fail the write with an error (nothing is damaged).
- A page read that returns fewer bytes than asked before the end of the file (POSIX allows it, e.g. on NFS or after a signal) is now read again instead of leaving the rest of the page zeroed. During recovery the zeroed bytes looked like the end of the WAL, so replay skipped the commits after them and a writable open trimmed them for good. Page reads and writes now use positioned I/O: one system call per page instead of a seek plus the read or write.
- Vacuum and WAL resize are crash-safe: both header slots name a valid layout afterwards (a torn newest slot no longer makes the file unopenable), a failure at any step leaves the database readable, `min_wal_size` can no longer shrink the WAL below 16 pages, and vectors committed since the last checkpoint are kept.
- After a crash leaves a torn WAL record, open moves the WAL head back to the last valid record, so later commits are no longer lost on the next crash.
- A crash right after a background checkpoint starts on an empty WAL no longer replays stale records from an earlier WAL cycle.
- A commit that fails after its COMMIT record is durable is kept in memory instead of being dropped by the next checkpoint, and vector dimension conflicts are refused before the commit becomes durable.
- Blocking checkpoints and optimize load the new snapshot before replacing the delta, so reads no longer briefly miss recent writes.
- A checkpoint whose header install fails now restores the previous WAL and header state. Previously the WAL was reset in memory first, so later commits could overwrite WAL records the on-disk header still named and lose committed transactions after a crash.
- Background checkpoints now start while other threads have write transactions open; their records so far are carried into the new WAL region. Previously checkpoints were refused while any transaction was open, so sustained concurrent writers could fill the WAL ("WAL buffer full").
- Blocking checkpoints and compaction now persist the WAL region heads and active region in the header. Previously a database reopened after a checkpoint could resume appending at a stale WAL offset.
- WAL recovery replays committed transactions in commit order instead of HashMap iteration order, which could previously produce nondeterministic post-crash state.
- Dynamically created labels, edge types, and property keys are WAL-logged, so their name-to-id mappings survive reopen without a checkpoint and ids can no longer be reattached to different names.
- Schema definitions made inside a transaction that rolls back no longer leak into the in-memory maps; concurrent transactions defining the same name share one reserved id.
- A blocking checkpoint can no longer erase a transaction that committed concurrently, and background checkpoints keep post-cut commits visible instead of hiding them until restart.
- A commit whose local WAL write succeeded no longer reports failure when the replication sidecar append fails; the sidecar is fenced (`sidecar_needs_repair`, `last_replication_error`) and requires repair/reseed rather than silently appending over a gap.
- MVCC version-chain and conflict keys use full-width typed keys; ids that collided under the old 20/12-bit packing (e.g. nodes 2^20 apart) no longer share version history.
- Corrupted or crafted database files and vector-index payloads now fail with clean errors instead of panics or unbounded allocations (checked bounds, monotonic offset validation, allocation caps, declared-size-exact decompression).
- Cosine IVF-PQ training normalizes vectors consistently with insert/search; `search_multi` honors `n_probe` and filters during candidate collection; a failed `train()` no longer permanently wedges the index; vectors without a node mapping are skipped instead of surfacing as node id 0.
- Node `bruteForceSearch` and Python `brute_force_search` leave out vectors whose distance is NaN (a NaN component). Previously they compared equal to every distance, so they could take top-k slots and leave the other results out of order.
- Seeded parallel k-means (`kmeans_parallel` with `KMeansConfig::with_seed`) returns the same centroids on any thread count. Its centroid update and inertia had added floats in an order set by how the work was split across threads, so the same seed gave a different index on a machine with another core count.
- Numeric options passed through the Node and Python bindings are range-validated with clear errors instead of silently wrapping (e.g. a negative cache size becoming a huge capacity, `cacheSize: 0` panicking).
- The TypeScript `transaction()`/`batch()` helpers preserve the original commit error instead of masking it with `No active transaction` from the cleanup rollback.
- Replica bootstrap works for primaries whose WAL is not 4MB (a custom size, the balanced or reopen-heavy profile, or a WAL shrunk by vacuum). Previously the replica opened the primary assuming the default size and failed with "WAL size mismatch".
- Reopening with default options after a default vacuum (which shrinks the WAL) works. Previously it failed with "WAL size mismatch".
- Fix ray schema ID reuse and add persistence integration tests (`5d73b0c`).
- Deleting an edge that lives in the snapshot after re-adding it now hides it, instead of leaving it visible forever and double-counting it. WAL replay drops dangling edges written by older versions, which previously made every checkpoint fail.
- Deleting a node deletes its vector embeddings, and ids of deleted nodes are no longer reused after a checkpoint and reopen.
- Lookups by out-of-range node ids (e.g. 2^62+1, `u64::MAX`) miss instead of panicking or returning another node's data, and the snapshot writer fails a checkpoint cleanly, before anything is installed, if a count exceeds a 32-bit field.
- Deadlocks: export racing a commit or background checkpoint, `stats()`/metrics scrapes racing a commit, MVCC reads racing GC or commits, and `node_by_key` inside an MVCC transaction (Kite `update_by_key`, upserts). MVCC readers follow one documented lock order.
- MVCC GC prunes label version chains, and chain truncation keeps the version the oldest active reader needs.
- Export -> import no longer loses node props, edge type names and edge props after a checkpoint; older export files still import. `createBackup`/`restoreBackup` with an extension-less path no longer overwrite an existing `.kitedb` despite `overwrite: false`, and backups taken under load are no longer torn.
- Replication: replicas receive label, edge-type and property-key names and translate the primary's ids to their own, so a Kite opened on a replica reads the primary's values by name (the mapping persists, is rebuilt on reseed, and is re-announced on promotion). Normal/Off-sync primaries publish buffered frames within ~100 ms and flag `sidecar_needs_repair` after a crash that lost buffered frames. Catch-up replay converges after a crash, reseed handles moved and swapped keys, and a permanently missing log range escalates to `needs_reseed`.
- Vector search: cosine with `normalize: false` ranks by true cosine; IVF/IVF-PQ return errors instead of crashing on wrong-length vectors or mismatched manifests (Node no longer aborts, Python raises `ValueError`); multi-query `Sum`/`Avg`/`Max` aggregate every candidate's distance to every query; a rejected `VectorIndex.set` no longer drops the node's existing ANN entry; `bruteForceSearch` cosine is correct for non-unit vectors and rejects zero vectors.
- Traversal `count()` always equals the number of results the traversal yields.
- Rust Kite: `insert()`/`upsert()` builders now label nodes with their type like `create_node`, and nodes created by `upsert_by_id` (which have no key) appear in `all()`/`count_nodes_by_type()` and get their type from `node_by_id` instead of `"unknown"`. With overlapping or empty key prefixes, `all("User")` no longer includes `user:admin:` nodes, and `node_by_id` no longer picks a type in HashMap order.
- Rust Kite: `update()`, `update_by_id()` and `update_by_key()` no longer commit a durable write transaction just to check that the node exists, so an update costs one fsync instead of two (about 2.5x faster with full sync).
- Rust pathfinding: with `max_depth`, Dijkstra, A*, `find()` and `find_k_shortest()` no longer miss a path when a cheaper but deeper route reaches an intermediate node first. Edges weighing NaN, infinity or a negative amount are skipped, where they used to stall the search queue or return wrong paths. Multi-target A* no longer returns a costlier target because its heuristic targeted an arbitrary one, and multi-target k-shortest ranks paths to every target.
- Rust pathfinding: `find_bfs()`/`bfs()` run a real breadth-first search instead of Dijkstra with a heap (about 30x faster on a 20k-node graph), and Dijkstra is about 1.5x faster.
- Rust traversal: `TraverseOptions` edge and node filters see the edge's and node's props (they were always empty), and `select()` limits which node props they load. `traverse()` after other steps reports depth as hops from the start (it restarted at 1), `both()` and `traverse(Both)` follow a self-loop once, and `raw_edges()` yields the edges of every step, honoring `take`, `unique` and filters, where it covered only the first step and panicked after `traverse()`.
- Rust traversal: `take(n)` stops expanding the last step once it has `n` results instead of building the whole frontier first.
- Rust Kite: `describe()` prints the real node and edge totals. A fresh database with 10 nodes printed `Nodes: 0 (snapshot: 0, delta: +10)`.
- Rust Kite: a `batch()`, `TxBuilder::execute()` or `transaction()` that fails inside an already-open transaction now rolls back only its own writes (to a savepoint taken when it joined) and returns its own error; the open transaction stays usable and commits the rest. Previously its earlier writes stayed in the open transaction and were committed with it. Successful nested calls still join the open transaction.
- Rust Kite: `transaction()` returns the closure's error when the rollback also fails, instead of the rollback error.
- With MVCC on, `create_node_with_id` and `upsert_edge_with_props` decide against the committed state plus the transaction's own changes instead of possibly stale version chains, so an upsert can no longer silently drop an edge and an explicit id can no longer duplicate a live node. `upsert_edge_with_props` / `Kite::upsert_edge` to a deleted endpoint now fails with `NodeNotFound` instead of storing a stray edge property.
- Node and edge pages (`nodes_page`/`edges_page`, `get_nodes_page`/`get_edges_page`) resume after their cursor even if the cursor's node or edge was deleted; previously the next page came back empty with `has_more = false`. Edge pages are ordered by (src, etype, dst), so edges added between pages no longer make pages repeat or skip edges.
- A stale primary rejects local commits while its replication sidecar needs repair. Previously the repair fence skipped the epoch check, so a primary superseded by a promotion kept committing.
- Replicas refuse a frame from a newer epoch that does not continue their log (e.g. after following a primary whose sidecar was a stale copy) and flag `needs_reseed`, and apply only contiguous runs of frames instead of skipping over a gap inside one pull.
- Metrics schema counts (`schema_labels`, `schema_etypes`, `schema_prop_keys`) count every committed definition; they dropped to 0 after a checkpoint.
- gRPC OTLP push no longer panics when called from inside a tokio runtime, and reuses one runtime and its connections instead of building both on every push.
- The OTLP circuit breaker no longer stays half-open for the life of the process after a probe failed before reaching the collector (bad payload, missing TLS file, bad bearer token); such errors no longer take the probe.
- Python: long-running calls (open/close, begin/commit, checkpoint, optimize, vacuum, export/import, backup/restore, replication catch-up, `wait_for_token`, index training, OTLP pushes) release the GIL; interrupted transactions are rolled back; `VectorIndex.search` no longer drops hits evicted from its cache; multi-hop traversals no longer return duplicates.
- Python: two `kite()` instances sharing node/edge definitions no longer read and write with each other's ids. Schema ids were stored on the shared definitions, so opening a second database redirected the first one's traversals and property writes.
- Python: `kite()` opens read-only databases and replicas. It looks schema ids up first and opens a write transaction only to create missing entries; previously it always began one, and a failed init leaked the open database handle.
- Python: batch inserts (`values([...])`, `values_many`) work inside `db.transaction()`/`db.batch()` and with MVCC, and roll back with the transaction. Previously they failed with "Transaction already in progress" or "bulk load requires MVCC disabled".
- Python: `close()`/`close_with_checkpoint_if_wal_over()` (and `Kite.close()`) no longer deadlock when another thread has a transaction open. The close-time checkpoint held the handle's exclusive lock while waiting for that transaction, which needed the lock to commit.
- Python: inserting no longer removes `key` from the caller's dict or returns a `NodeRef` whose props alias it, and an insert executor can run again after its transaction rolled back.
- Python: `Kite.check()` returns the warnings it adds; they were appended to a temporary copy and lost.
- Python: the `_kitedb.pyi` type stubs match the native module (methods such as `vacuum`, `commit_with_token`, the replication calls, and options classes were missing; nonexistent methods and wrong signatures such as `should_checkpoint(None)` and `OpenOptions(lock_file=...)` are gone), and a test keeps them in sync. `BruteForceResult` is exported.
- Node: retried insert/upsert executors (e.g. `batchAdaptive` after WAL-full) keep their props, and `whereNode`/`whereEdge` callbacks are released when the traversal is collected.
- Node: Kite traversal filters apply where they are written. `whereNode(f).take(n)` returns up to n matching nodes (the limit was applied before the filter, so it could return none), a second `whereNode`/`whereEdge` narrows the first instead of replacing it, and a filter between two hops filters the first hop instead of the last. Unfiltered `nodes()`, `edges()` and `count()` no longer load every result's props.
- Node: schemas using `withDefault()` open. `kite()`/`kiteSync()` rejected them with "Missing field `propType`"; the defaults are now applied on insert.
- Node: edge props named `src`, `dst` or `etype` no longer overwrite the edge's identity in `whereEdge` callbacks.
- Node: `batchAdaptive` checkpoints again after shrinking a batch that hit a full WAL. Previously it checkpointed only once and then failed.
- Playground graph view, path finding and impact analysis work again on the native engine.
- Group commit could lose acknowledged commits, or replay stale records of an earlier WAL cycle, after a crash: a commit's header was written before the WAL bytes it named were flushed. The WAL is now flushed first.
- A commit that failed before it became durable (for example on a header write error) came back after the next commit and a reopen. Its COMMIT record is now discarded and the transaction aborted.
- MVCC: a transaction that began while another commit was being applied could read the old value and then the new one within one snapshot, or overwrite that commit's write without a conflict. A commit's timestamp, version history and data now become visible to new transactions together.
- A WAL holding a vector whose dimensions disagree with its property's store (left behind by older versions) no longer makes the database unopenable. Replay skips and logs it, keeping the vector committed first.
- MVCC: reads no longer return stale values after a commit made with no other transaction open, or after a checkpoint. Version chains now hold only history for older readers, and the latest state always comes from the delta and snapshot. This also fixes Kite delete/upsert/update/set_prop/unlink, replica apply and `check()` acting on stale state.
- MVCC: a transaction keeps seeing nodes and edges deleted after it began, with their props, labels, keys and edges, in point reads, `out_edges`/`in_edges`, `list_nodes`/`list_edges`, `node_key` and `node_by_key`.
- MVCC: setting a node or edge property now conflicts with a concurrent delete of that node, edge or edge endpoint, instead of committing a write to a deleted entity. Adding or removing a label no longer conflicts with transactions that only checked that the node exists.
- Recreating a deleted node by id (`create_node_with_id`, `upsert_node_by_id`, Kite `upsert_by_id`) works: the node is visible, starts fresh (the old node's props, labels, key and edges stay hidden), and survives checkpoint and reopen. Before, a recreated snapshot node was invisible and lost on reopen, and a delete and recreate in one transaction brought the old node back. With MVCC, transactions that began before the recreate keep seeing the old node.
- `edge_exists` no longer reports edges of deleted nodes.
- WAL replay ignores a repeated create of an existing node instead of wiping its key and properties.
- Replica reseed no longer forces a checkpoint between removing stale nodes and recreating them.
- A checkpoint now decodes the new snapshot's vector stores before installing it. A snapshot whose vector store did not decode used to be installed, after which the vectors read as missing and every later checkpoint failed.
- A checkpoint no longer fails on an edge whose endpoint no longer exists (left by older versions or by write transactions racing a node delete). It drops such edges, with their props, and logs how many. Previously every checkpoint failed the same way and the WAL filled up.
- Checkpoints drop vectors of nodes that no longer exist instead of copying them into every snapshot.
- A replication primary in Normal or Off sync mode now publishes and fsyncs its buffered sidecar frames, and persists the manifest, before a checkpoint resets the WAL. A crash right after a checkpoint no longer leaves the sidecar fenced for a reseed. If the publish fails, the sidecar is fenced for repair and the checkpoint still completes.
- Read-only opens no longer replay a WAL record that extends past the WAL head.
- Node: DB-backed `dijkstra`/`kShortest` honour zero edge weights and reject negative or NaN weights on the edges they relax; both were silently replaced by 1.0. `JsGraphAccessor.addEdge` rejects negative and NaN weights, and `JsGraphAccessor.traverseSingle` honours its direction (it always followed outgoing edges).
- Node: `getNodesPage`/`getEdgesPage` continue after the cursor's node or edge was deleted; previously the next page was empty with `hasMore: false`, ending iteration early. Edge pages no longer count every edge a second time for `total`.
- Node: `JsIvfIndex`/`JsIvfPqIndex` search reuses the parsed manifest while the JSON is unchanged instead of parsing it on every query (~10x faster per query on a 27 MB manifest). `exportToObject` builds its result without an intermediate JSON tree, and `importFromObject` reads nodes and edges straight from JS, so an export holding node ids or integer props above 2^32 imports instead of failing with "invalid type: floating point".
- Deleting a node created since the last checkpoint scanned every edge added since then, so committing many such deletes was quadratic: 10k deletes among 1M uncheckpointed edges took about 95 s of CPU. Each delete now costs the node's own edges (about 0.1 s for the same commit).
- Deleting an edge deletes its properties. Re-adding the edge (in a later transaction or the same one, by `add_edge`, a batch, `add_edge_with_props` or an upsert) used to bring the old properties back, from the delta or from the snapshot, and they survived checkpoint and reopen. A node recreated by id no longer inherits the properties of its old edges either.
- The core write calls `set_node_prop`, `delete_node_prop`, `add_node_label`, `remove_node_label`, `set_edge_prop`, `set_edge_props` and `delete_edge_prop` (also used by the low-level Node and Python `Database` APIs, which throw an `Error` / raise `NotFoundError`) fail with `NodeNotFound` / `EdgeNotFound` on a missing node or edge, as the Kite API does. They used to succeed: a deleted node, or an id never created, then read back those props and labels (`node_prop`, `node_props`, `node_labels`, `node_has_label`) until the next checkpoint, and again after a reopen; a prop written to a missing edge appeared once the edge was added. Reads no longer count such leftovers as a node, and WAL replay skips them.
- Without MVCC, a commit that writes to a node or edge another transaction deleted after the write was checked fails with `NodeNotFound` / `EdgeNotFound`, with nothing recorded. It used to leave props, labels, an edge or a vector on the missing node. Adding an edge and then deleting one of its endpoints in the same transaction no longer leaves the edge, and its props, visible after the commit.
- `set_node_vector` and `delete_node_vector` (and the Node and Python `Database` vector calls) fail with `NodeNotFound` for a node the transaction does not see. `set_node_vector` used to accept any id (never created, deleted earlier, or deleted earlier in the same transaction), and `node_vector` / `has_node_vector` then returned the vector until the next reopen. With MVCC, setting a vector now conflicts with a concurrent delete of its node.
- `node_vector` inside the transaction that set the vector returns it normalized, exactly as it reads after the commit, a reopen or a checkpoint (the store normalizes on insert). It used to return the raw input until the commit.
- With MVCC enabled, concurrent `begin` calls could leave the next transaction id at or below an id already handed out; a commit persisted it, and after reopen that id was issued again, so two transactions' WAL records could share one id. Begin now only ever raises it.
- With group commit enabled, background checkpoints often declined with "no BEGIN record found for open transactions": a transaction counted as open until its committing thread woke after the batch's flush, after its COMMIT was already durable, so a checkpoint taken in between dropped its records and the next one could not start. A transaction now stops counting as open as soon as its COMMIT (or ROLLBACK) is written.
- A blocking `checkpoint()`, optimize, vacuum or `resize_wal` could wait indefinitely while `background_checkpoint()` was called in a loop: each new background run claimed the checkpoint ahead of the waiting operation (measured: 0-2 blocking checkpoints in 1.5 s against about 100 background runs). While such an operation waits, `background_checkpoint()` now returns `CheckpointDeclined` (the auto-checkpoint skips quietly), so the operation waits for at most the run in progress.
- A thread that ended (or died) with a transaction still open left it open forever, so every later blocking `checkpoint()`, optimize, vacuum and `resize_wal` waited for it indefinitely. Such a transaction is now rolled back.
- Cosine IVF indexes normalize their centroids after training, as IVF-PQ does. Previously the raw cluster means were shorter for spread-out clusters, so inserts and probes favored tight clusters and recall dropped.
- `IvfIndex` search skips vectors without a node mapping instead of returning them as node 0 past the search filter, and a failed `IvfIndex::train` keeps its training buffer, so adding more vectors and retrying works instead of failing forever with a dimension mismatch.
- Exact vector search no longer panics ("comparison function does not correctly implement a total order") or misorders results when distances overflow to NaN, and a NaN distance no longer freezes the IVF/IVF-PQ top-k so that later, closer vectors are dropped.
- Normalizing a vector whose squared components overflow or underflow f32 (components around 1e20 or 1e-25) yields its unit direction. Previously such vectors became all zeros or stayed unnormalized, and cosine indexes ranked them wrongly.
- Zero clusters, zero dimensions, `PqIndex::search` with `k = 0` and a vector store with `row_group_size = 0` return errors (or empty results) instead of panicking.
- Vector store compaction (`run_compaction_if_needed`, `force_full_compaction`, `clear_deleted_fragments`) leaves manifests that reload: it keeps the store totals and deletion bitmaps consistent, removes emptied fragments, and never reuses a fragment id.
- TUI: keyboard shortcuts and text input work (the handlers read a `key` field opentui's events don't have), opening a database no longer fails with "this.db.nodeTypes is not a function", q/Esc close the database before exiting, nodes created by an import show their keys, node details show edge endpoints instead of `undefined`, and `bun run build` works.
- Playground: concurrent database opens no longer leak a handle, a failing close still removes its temp directory, and snapshots are read in one synchronous pass so concurrent requests can't tear them. `/api/replication/log` polls skip segments before the cursor (about 8x faster at the log head with 137 segments). The client handles failed status, path and impact requests, ignores responses superseded by a newer request or a database switch, clears highlights when another database is opened, and lays out nodes that arrive while a layout is running instead of stacking them at the origin.
- `examples/ts-package` installs @kitedb/core 0.2.18 (its lockfiles resolved 0.2.7), and its `dev` and `typecheck` scripts work.
- The npm package README told users to `npm install kitedb`, which is unpublished; it now says `@kitedb/core`.
- Closing or dropping a database opened with MVCC returns at once. Previously it waited out the background GC thread's sleep, up to the GC interval (5 s by default).
- With MVCC on, a commit no longer keeps the transaction's read and write sets in memory. Previously, while any other transaction was open, every committed transaction stayed tracked for at least the 60 s retention period, and GC passes and conflict-index pruning scanned them all.
- With MVCC on, commits made while a long-running transaction is open no longer slow down once more than 100,000 keys have been written since it began. Previously each such commit re-sorted the whole conflict index.

### Security
- TS replication admin auth helper: `mode` is required (`'none'` disables auth explicitly); a config without one allowed every request. A client-certificate header no longer authorizes by its mere presence: it is trusted only with `trustForwardedClientCert: true` and an `mtlsSubjectRegex`, which must now match the whole header value, and the mTLS modes need that or an `mtlsMatcher`. Bearer tokens are compared in constant time.
- Python wheels build against pyo3 0.29.3; pyo3 0.24 had two advisories (RUSTSEC-2026-0176, RUSTSEC-2026-0177).
- Python replication admin auth (`ReplicationAdminAuthConfig`), matching the TS helper: `mode` is required, and a config without one raises `ValueError` instead of allowing every request (`mode="none"` disables auth explicitly). Bearer tokens are compared in constant time over SHA-256 digests. A forwarded client-certificate header (`mtls_header`, default `x-forwarded-client-cert`) no longer authorizes just by being present: it counts only with the new `trust_forwarded_client_cert=True` and an `mtls_subject_regex` that must match the whole header value. The mTLS modes need that or an `mtls_matcher`, and other configs raise `ValueError`. Configs that relied on the default mode or on the header must be updated.
- Playground: uploads are stored under a fixed name in a private temp directory, so a crafted filename can no longer write outside it. The server binds `127.0.0.1` by default (`PLAYGROUND_HOST`), allows only listed CORS origins (`PLAYGROUND_ALLOWED_ORIGINS`), opens databases only inside `PLAYGROUND_DATA_DIR`, and disables replication admin endpoints unless `REPLICATION_ADMIN_TOKEN` or mTLS is configured (tokens compared in constant time).
